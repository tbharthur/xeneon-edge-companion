# Custom dashboard widgets

Updated: 2026-11-11.

EdgeCompanion has no plugin system; custom widgets were added to the local source and the app rebuilt/reinstalled. Its built-in web page widget can display a web dashboard, but the session reported only one such widget supported.

## Arthur's layout and design preference

Arthur requested the two new widgets on the main screen and no launcher/shortcuts. The installed layout is one page. Since 2026-11-04 the quotas take a large (2×2) slot and the recorder a tall (1×2) slot beside it; before that they were stacked, each half the height. Layout controls are in Settings → Dashboard → Widget layout. Earlier instructions to swipe to separate second/third pages are superseded.

Arthur found the first UI too small and the recorder too empty. The redesign uses larger type, account tiles, compact bars, a large round recording control, a large timer and a transcription progress ring. Final dashboard height was reduced to preserve the menu bar; see [split mode](split-mode.md).

## Account quotas

- Reads the same local quota feed and usable/blocked rules as Devboard, covering eight accounts: six Claude, then two Codex. This is broader than the app's original Claude Code/Codex usage widget.
- Shows 5-hour, weekly and Fable-weekly usage/reset information, plan and active-account indication. Usage thresholds are amber at 75% and red at 90%.
- The redesigned account tiles emphasize whichever usage limit is closest to exhaustion, with three small bars underneath. Blocked tiles turn red; Fable-blocked tiles turn amber. Both show the release time; the header counts ready/blocked accounts. A reset-time formatting fix preserves minutes for dates beyond today.
- Tiers (2026-11-03, Arthur): Claude Ultra plans (feed `plan` containing "Ultra"; currently gmail and arthur) are the top tier. They sort first among Claude accounts even when blocked and sit in a left column of larger tiles with a plan tag, a big number and labeled horizontal bars with percentages. The Team 5x seats, cascade and the Codex accounts form the second tier in a 3×2 grid of smaller tiles on the right. With only one tier present the original grid is used.
- Groups (2026-11-04, Arthur): the widget shows three labeled groups top to bottom: Claude Ultra as full-width rows (number left, labeled bars right), Claude Team as a tile grid, then Codex as a tile grid. Each group label carries its ready and blocked counts; the header keeps only the feed-offline pill. Grouping lives in EdgeCore `QuotaBucket`, with a test. This replaces the left-column tier split.
- One row per account (2026-11-11, Arthur): the widget was too crowded; what matters most is each account's email, whether it is blocked, and when a blocked account comes back. Each row shows a status dot, the email (feed `email`, falling back to the label), and "Ready · N% used", "Blocked", or amber "Fable blocked" when only Fable is out. A blocked row's return time sits at the right edge in the same shape on every row: the clock time in bold white, with a smaller red (amber for Fable) date under it ("12:00 PM" over "Fri, 11/13"), so the times line up (Arthur's layout, same day). Times round to the nearest minute, so a 6:59:59 reset reads 7:00 PM. The per-window bars, big percentages and the active-account bolt are gone. Rows stay under small Claude Ultra / Claude Team / Codex labels; the header shows "N of M ready". Below about 420 points wide the status sits under the email. The status rule is EdgeCore `QuotaAccountView.headline`, with a test. This replaces the tile and labeled-bar designs above.
- Polls every minute while visible. If the feed fails, keeps the last values greyed out with a feed-status indication.
- Classification tests passed and small/large/wide layouts were rendered and refined. The redesigned preview used sample data with blocked-account examples while the Edge was asleep.

## Call recorder

- Integrates the existing meeting-recorder script and pipeline. The Poly Sync 20 speakerphone was permanently removed (2026-11-11): the widget no longer forces an output device (the `recorderOutputDevice` setting and the `RECORD_AUDIO_FORCE_OUTPUT_DEVICE` variable are gone, and any stored value is ignored), so the recorder captures from whatever output is the system default. The recorder chooses its own mic: Shure MV7 first, then the Insta360 webcam mic. The idle Record caption that referred to the Poly button was dropped.
- Stop requires two taps within three seconds. During recording the widget shows a pulsing red indicator and elapsed time; the redesign uses a large round Record/Stop control and big timer.
- After stopping, shows Transcribing with percentage and recording duration, then Sending to Discord. The redesigned transcription state has a progress ring.
- Idle state reports the last call's date, duration and result: sent to Discord, transcript saved but Discord handoff failed, no audio captured, or recording did not start.
- Supporting recorder pipeline status writes were added for recording, transcribing, sending and done. A stale previous-call 100% transcription display and small-size truncation were fixed.
- State tests passed and layouts were rendered across states. Start/Stop invocation and error handling were exercised with a stand-in recorder script; pipeline status was exercised using fake input and an unreachable Discord endpoint to avoid posting. A real 9:46 test recording later completed the pipeline and was reported sent to Discord.
- Mic mute (added 2026-11-03): a round mic button the same size as Record, side by side under the header with captions beneath each, mutes every physical microphone at the device level (CoreAudio input mute), so Teams, Zoom, Meet, phone calls and the recorder's mic channel all go silent, whichever mic the app picked. Virtual and aggregate inputs (such as Microsoft Teams Audio) are skipped. It reads "Muted" (amber) only when every physical mic is muted; one tap mutes all unless all are already muted. State is re-read every second, so mutes made elsewhere show up. The caption names the mic an app has open (joined with "+" if several, e.g. the recorder plus Teams on different mics), falling back to the system default. On 2026-11-03 Teams was capturing from the Shure MV7 while another device was the system default, which is why it mutes every mic rather than only the default.
- Mute verification: rule tests pass; the panel showed equal Record and mic circles with the mic captioned "Mic on · Shure MV7" while Teams held the MV7; a mute of one non-default device was read back and correctly left the state at "Mic on". The muted look and a real tap were not exercised because Teams held the MV7 open.
- Stacked layout (2026-11-04): in a card taller than it is wide (Arthur's layout: quotas large, recorder tall), Record and the mic each sit in their own rounded panel, stacked, with a Last call strip at the bottom while idle. The record panel tints red while recording and blue while transcribing or sending; the mic panel tints amber when muted. Wider cards keep the side-by-side layout. Checked on the panel at the 480-point split width in the idle state.
- Phone controls (2026-11-05, Arthur): a third panel under the mic holds a round green Answer and a red Hang Up, for iPhone calls taken on the Mac through the Phone app (Continuity). Answer picks up a ringing call; with nothing ringing it opens or launches Phone. Hang Up declines a ringing call or ends the current one, and is dimmed when there is no call. Captions read Phone/Hang Up, Answer/Decline, or On call/Hang Up; the panel tints green while ringing. Wider cards put the pair, stacked, in a third column. Arthur planned to widen the dashboard to fit them. Enlarged the same day at Arthur's request: in the tall card the pair is as wide as fits side by side, capped at the size that would make Record, the mic and the phone buttons equal. At the 600-point dashboard the phone circles went from 53 to 65 points, with Record and the mic at about 96. From about 720 points wide all three are about 85-86. In wide cards the pair matches Record and the mic.
- How it works: there is no public way to see or control these calls. CallKit's call observer is unavailable to AppKit apps, and the private call center (`TUCallCenter`) was tested and rejected by `callservicesd` for lacking the "access-calls" entitlement. So the widget reads the call windows through Accessibility, as VoiceOver does, and presses their own Answer, Decline and End buttons. The labels come from the system's own strings (FaceTimeNotificationUI and ConversationKit), in the Mac's languages plus English and Korean. Logic and tests are in EdgeCore `PhoneCall`; the reader is `PhoneController`.
- Fail-safe rules: a control is offered only when exactly one matching button is on screen. Ringing needs one Answer and one Decline in the same window. "Accept" is not treated as Answer, because calendar invitations offer Accept/Decline too. Anything ambiguous offers nothing to press. Every tap re-reads the screen and presses only if the call is still in the state the tap was meant for.
- Cost: macOS launches Phone when a call arrives (seen in the 2026-11-05 3:01 PM call's system log), so nothing is read while Phone and the call-alert services are not running. While Phone runs, call windows are read once a second and Phone's main window, slow to read (about 17-50 ms), every fifth second with its contact and recents lists skipped. Measured app CPU during a call was about 1-2%.
- Where calls appear (system log of the 3:01 PM incoming call, and a live call): the ringing alert is a Notification Center custom alert drawn by `FaceTimeNotificationViewBridgeService` and `FaceTimeNotificationExtension`. If dragged, it becomes a Phone window. The in-call window is a Phone window (`SceneWindow`, subrole `AXUnknown`) with an `End` button. Phone's main window is the standard window titled "Phone".
- Verification: call-state tests pass. During Arthur's real outgoing call at 4:49 PM on 2026-11-05, the installed app found the in-call End button. The Edge panel showed "On call" with a red Hang Up, and nothing was pressed. When the call ended, the widget went back to idle and Phone quit itself. Idle, ringing, active and no-Accessibility layouts were rendered at 600, 720 and 800-point dashboard widths and in a wide card. **Unverified until a real incoming call:** that the Notification Center alert's Answer and Decline buttons are readable through Accessibility with those labels, and that pressing them (and End) works. The app logs the call windows' button labels to `~/Library/Logs/EdgeCompanion/EdgeCompanion.log` (lines starting `phone:`) on every state change, to check this after the first incoming call. If ringing is not detected, Answer only opens Phone and Hang Up stays dimmed.

Verification boundaries: rendered previews often used sample data while the panel slept; the final installed layouts were not all observed directly on the panel.

## Monitor volume

- Added 2026-11-11 at Arthur's request: a tall mixing-desk fader for the LG ULTRAWIDE's own speaker volume, with a Mute key that lights red. It sits at the right end of the dashboard page (quotas, recorder, monitor volume). Arthur planned to widen the dashboard to make room.
- macOS has no software volume for the LG's display audio, so the widget uses DDC/CI: MCCS 0x62 (volume, 0-100 on the LG) and 0x8D (mute: 1 muted, 2 unmuted). It targets the first external display that is not the Edge, and only those two codes (EdgeCore `MonitorAudioVCP`). The Edge stays limited to its colour codes.
- On the Edge a vertical finger drag arrives as scroll events and a tap as a click, so the fader uses an AppKit input view: drag moves it with the finger, a tap jumps to that point, momentum after lifting is ignored. Writes collapse to the newest value while the bus is busy.
- Reads run every 4 seconds while visible and pause for 2.5 seconds after a change, so the fader never jumps back mid-drag.
- The LG drops the first DDC request frame and answers an empty "not ready" reply. Reads to the monitor therefore send the request twice, 10 ms apart (as m1ddc does), then wait 40 ms. Measured 2026-11-11: about 1 in 10 reads answered with one frame, 8-9 in 10 with two, mute (0x8D) included. Edge reads are unchanged.
- A missed read is normal on the shared bus (MonitorControl, which Arthur keeps running, uses it too). The widget shows "Can't reach" only after three missed volume reads in a row. A missed mute read keeps the last known state; a monitor that never reports mute is asked five times, then the widget tracks its own taps.
- MonitorControl's volume keys change the same LG volume; the widget picks those changes up on its next read.
- Running `m1ddc ... get` while the widget polls returns garbage (for example 8224) because the replies collide; the app checks the VCP code in each reply, m1ddc does not. Writes are unaffected.
- Verification (2026-11-11): rule tests pass; the panel showed the LG's real volume (43%, then 35% and 50% after changes made elsewhere). Muting the LG via DDC held mute for 10 seconds with the volume unchanged. After the call, synthetic clicks and scrolls on the installed widget were read back from the LG: Mute set 0x8D to 1 and the widget showed Muted (red key, struck-through level); a second tap unmuted; a tap low on the track set volume 25 and one at the middle 50; a 100-point scroll moved it 50→27 and back to 50. Not yet exercised with a finger on the panel itself.
